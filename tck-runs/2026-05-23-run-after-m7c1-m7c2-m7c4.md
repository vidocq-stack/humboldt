## Catégorisation des 60 failures

### Cluster A — REST Client absent (~18 tests) → **M7c.5 Cyrano MP Rest Client**

```
RestClientSpanTest.setUp:114 Failed to create rest client
RestClientSpanDefaultTest.setUp:95 Failed to create rest client
RestClientSpanDisabledTest.setUp:97 Failed to create rest client
W3BaggagePropagationTest.setUp:91 Failed to create rest client
W3PropagationTest.setUp:91 Failed to create rest client
JaxRsServerAsyncTest.* → IllegalState: No RestClientBuilderResolver implementation found!
```

Cause : pas d'implémentation MicroProfile Rest Client 4.0 dans le classpath du
déploiement Arquillian. Solution : ajouter `cyrano` (et ses runtime deps) au
classpath via `HumboldtDeployableContainer`.

### Cluster B — Spans manquants ou en trop (~15 tests) → **M7c.6/7 filter logic**

```
RestSpanDefaultTest.span → expected [0] but found [1]
RestSpanDefaultTest.spanName → expected [0] but found [1]
RestSpanDisabledTest.span → expected [0] but found [1]
JaxRsClientAsyncTest.testIntegrationWithJaxRsClient → expected [3] but found [1]
JaxRsClientAsyncTest.testIntegrationWithJaxRsClientAsync → expected [3] but found [1]
```

Deux sous-causes :
- `RestSpanDefault/DisabledTest expected 0 found 1` : on émet des spans même
  quand `otel.sdk.disabled=true` ou pour les requêtes internes. Vérifier le
  filter HTTP de `humboldt-rest`.
- `JaxRsClientAsync expected 3 found 1` : on a 1 SERVER span mais pas les 2
  CLIENT spans attendus. Manque le **M7c.7 ClientFilter** (filter JAX-RS Client
  qui crée un span SPAN_KIND_CLIENT autour de chaque appel sortant).

### Cluster C — http.route incorrect (~1 test) → **M7c.8 UriInfo.getMatchedTemplates()**

```
RestSpanTest.spanNameWithoutQueryString
  expected [/<uuid>/span/1?id=1] but found [/span/1]
```

Le filter humboldt-rest remonte le path **après stripping du context root**,
alors que la spec attend le path **complet incluant le context** + paramètres
de path. Solution : utiliser `UriInfo.getMatchedTemplates()` et concaténer
avec `UriInfo.getBaseUri()`.

### Cluster D — Autoconfigure SPI (~3 tests) → décision (déféré ?)

```
CustomizerSpiTest.testCustomizer → expected [test-value] but found [null]
ResourceSpiTest.testResource → expected [test1] but found [null]
SamplerSpiTest.testSampler → expected [false] but found [true]
```

Le TCK appelle des SPI OTel SDK autoconfigure (`AutoConfigurationCustomizerProvider`,
`ResourceProvider`, `ConfigurableSamplerProvider`). Humboldt n'utilise pas OTel
SDK autoconfigure côté runtime ; le bridge `humboldt-tck` réinjecte le SDK
fixture mais ne pipe pas ces SPI vers le runtime Humboldt.

Décision : à arbitrer. Soit on étend le bridge pour propager les customizers
vers `HumboldtAutoConfigure`, soit on documente l'exclusion (Humboldt n'a pas
de pipeline `AutoConfigurationCustomizer` natif, c'est conforme).

### Cluster E — SDK metric / log absents (~23 tests) → **M4b** + **M5b**

Tous les tests `Metrics*Test` (DoubleCounter, LongCounter, Histogram, Observable,
JVM metrics) et `Logs*Test` (JulHandler bridge) — tests cités par la roadmap
M7c comme dépendants de l'implémentation SDK metric / log complète.
